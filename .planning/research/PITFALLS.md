# Domain Pitfalls - PDF Editor (Electron + JavaScript)

**Domain:** Desktop PDF editor for Windows (Electron + JavaScript)
**Researched:** 2026-05-15
**Confidence:** HIGH (verified via Context7 docs for pdf-lib, PDF.js, and Electron ecosystem)

---

## Critical Pitfalls

Mistakes that cause rewrites, data loss, or completely broken features.

---

### Pitfall 1: pdf-lib Destroys Incremental Saves and Existing Digital Signatures

**What goes wrong:** pdf-lib loads a PDF and re-serializes it entirely via \PDFDocument.save()\. This discards the incremental save chain that many PDFs use. If the original PDF was saved incrementally (common with Adobe Acrobat, Microsoft Word PDF export, or digitally signed documents), the output is a fully re-written PDF that:

- Strips the incremental save history
- **Invalidates existing digital signatures** (the cryptographic hash chain is broken)
- May lose metadata set by the original authoring tool
- Can change the file size and structure in ways some validators flag

**Why it happens:** pdf-lib does not support incremental save (append-only). Every \save()\ call re-serializes the complete document from scratch. This is by design - the PDF.js and pdf-lib maintainers consider incremental save a legacy feature.

**Consequences:**

- User opens a digitally signed PDF, makes a small edit (e.g., fills one form field), saves -> the original signature is silently invalidated
- User opens a PDF generated by Adobe Acrobat with incremental saves -> metadata like "Last Modified by" is lost
- Some PDF viewers may refuse to open a PDF that was originally signed but now has an invalid signature chain

**Prevention:**

- **Before any save operation, check for and warn about existing digital signatures:**
  - Use pdf-lib's \PDFDocument.isSigned()\ or check the \/Signature\ array in the document catalog
  - If a signature exists, show a clear warning: "This document contains a digital signature. Saving will invalidate it."
  - Offer "Save As" with a new filename to preserve the original
- **Before any save, check for incremental saves:**
  - pdf-lib loads these fine but the output loses the incremental chain
  - For personal use, this is acceptable but document the limitation
- **Implement "Save" (overwrite) vs "Save As" (new file) distinction:**
  - "Save" overwrites the original - warn about signature invalidation
  - "Save As" creates a new file - the original is untouched, signatures preserved

**Detection warning signs:**

- \pdf-lib\ throws \EncryptedPDFError\ on encrypted PDFs (related to Pitfall 2)
- After saving, the PDF's file size changes dramatically
- After saving, the document's metadata (author, creation date) is reset
- After saving, a previously-valid digital signature shows as "invalid" in Acrobat

**Phase to address:** Phase 1 (Document Manager + Save) - this is a fundamental document lifecycle concern

### Pitfall 2: Encrypted PDFs Cannot Be Modified (Silent Failure)

**What goes wrong:** pdf-lib throws an \EncryptedPDFError\ when loading an encrypted PDF. The error message is clear, but if not handled gracefully, the app will crash or show a raw JavaScript error. Worse, the \ignoreEncryption: true\ option exists but **does not actually decrypt** - it just suppresses the error and loads a garbage document that will fail on any modification.

**Why it happens:** pdf-lib does not implement PDF encryption/decryption. The \ignoreEncryption\ flag was added for backwards compatibility but does not decrypt the file content.

**Consequences:**

- User opens a password-protected PDF -> app shows a raw error or loads broken content
- User tries to fill form fields in an encrypted PDF -> cryptic failure deep in the stack
- The \ignoreEncryption: true\ option gives false confidence - the document "loads" but modifications fail

**Prevention:**

- **Catch \EncryptedPDFError\ explicitly** when loading PDFs:
  `javascript
  try {
    const pdfDoc = await PDFDocument.load(bytes);
  } catch (err) {
    if (err instanceof EncryptedPDFError) {
      // Show user-friendly dialog: "This PDF is encrypted. Please enter the password."
      // Or: "This PDF is password-protected and cannot be edited by this tool."
    }
  }
  `
- **Do NOT use \ignoreEncryption: true\** - it serves no useful purpose for an editing app
- **Consider offering a password entry dialog** (Phase 2+) - though pdf-lib doesn't support decryption, you could call an external tool or guide the user to decrypt elsewhere

**Detection warning signs:**

- \EncryptedPDFError\ thrown during \PDFDocument.load()\
- Document loads but all operations fail silently
- PDF renders fine in PDF.js (which handles encryption) but pdf-lib fails

**Phase to address:** Phase 1 (Document Manager) - error handling for load

### Pitfall 3: PDF.js CMap Loading Is Mandatory for Non-Latin Text Extraction

**What goes wrong:** PDF.js does not ship CMap files (character mapping tables) by default. Without CMap files, text extraction for CJK (Chinese, Japanese, Korean), Arabic, Devanagari, and other non-Latin scripts either returns empty strings, garbled characters, or fails entirely. The text search feature will silently miss all non-Latin text.

**Why it happens:** CMap files are large (hundreds of KB each) and PDF.js defers loading them to reduce initial bundle size. They must be explicitly provided via \cMapUrl\ and \cMapPacked\ configuration.

**Consequences:**

- User searches for text in a Chinese PDF -> no results found (even though text exists)
- User copies text from a Japanese PDF -> garbled characters or empty strings
- The app appears broken for international users

**Prevention:**

- **Always configure PDF.js with CMap URLs:**
  `javascript
  const loadingTask = getDocument({
    data: pdfBytes,
    cMapUrl: './cmaps/',         // Ship CMap files with the Electron app
    cMapPacked: true,
    standardFontDataUrl: './standard_fonts/',
  });
  `
- **Ship CMap files in the Electron app package** - they are part of the \pdfjs-dist\ npm package under \
ode_modules/pdfjs-dist/cmaps/\
- **For Electron distribution**, copy CMap files to an assets directory and reference them from the packaged app path
- **Handle missing CMap gracefully** - if CMap loading fails, log a warning and fall back to empty text extraction (don't crash)

**Detection warning signs:**

- Text extraction returns empty strings for known non-Latin documents
- Search returns no results for documents that clearly contain text
- PDF.js console warnings about missing CMap files

**Phase to address:** Phase 1 (PDF.js Rendering + Text Search)

### Pitfall 4: pdf-lib Form Fields Require Font Embedding for Non-Latin Characters

**What goes wrong:** The default font for pdf-lib form fields is Helvetica, which only supports the WinAnsi character set (basic Latin + some symbols). If a user types non-Latin characters (Chinese, Arabic, emoji, etc.) into a form field, pdf-lib will throw an error on \save()\ or produce garbled output.

**Why it happens:** Standard PDF fonts (Helvetica, Times, Courier) are limited to 256 characters. pdf-lib's default form field appearance uses these standard fonts. Non-Latin characters require embedding a custom font via \@pdf-lib/fontkit\.

**Consequences:**

- User fills a form with Chinese characters -> \save()\ throws an error
- User fills a form with emoji -> garbled text in the saved PDF
- The app crashes during save with a confusing error message

**Prevention:**

- **Register fontkit early** (before any form operations):
  `javascript
  import fontkit from '@pdf-lib/fontkit';
  pdfDoc.registerFontkit(fontkit);
  `
- **For form fields with non-Latin text, update appearances with a custom font:**
  `javascript
  const ubuntuFont = await pdfDoc.embedFont(ubuntuFontBytes);
  form.getTextField('Name').setText('ChineseName');
  form.updateFieldAppearances(ubuntuFont);
  `
- **Use \updateFieldAppearances(font)\ after any text field modification** - this is the critical step that most developers miss
- **Consider bundling a Unicode-capable font** (e.g., Noto Sans) with the app so non-Latin text works out of the box

**Detection warning signs:**

- \save()\ throws an error about unsupported characters
- Form fields display as squares/tofu (missing glyphs) in the saved PDF
- User reports "weird characters" or blank form fields after saving

**Phase to address:** Phase 2 (Form Filling)

### Pitfall 5: pdf-lib Does NOT Support Text Editing - Only Overlay

**What goes wrong:** Developers assume pdf-lib can "edit text in existing PDFs" because the project requirement says so. pdf-lib **cannot** modify existing text content. It can only:

- Draw new text on top of existing text (overlay)
- Add annotations
- Modify form fields

True text editing (replacing "teh" with "the" in the PDF's content stream) requires parsing PDF text operators (Tj/TJ), understanding font CMaps, and reconstructing content streams - which pdf-lib explicitly does not support.

**Why it happens:** The pdf-lib README says "editing content within form fields" but the word "editing" is ambiguous. It means editing form field *values*, not page text.

**Consequences:**

- Phase 4 (Text Editing) hits a hard wall - pdf-lib cannot deliver the feature
- User expects to click on existing text and type corrections -> app can't do this
- Time wasted trying to make pdf-lib do something it fundamentally cannot do

**Prevention:**

- **For v1, implement text editing as overlay:**
  - Detect the text to replace (via PDF.js text extraction + user selection)
  - Draw a white rectangle to "cross out" the old text (pdf-lib \drawRectangle\)
  - Draw the replacement text on top (pdf-lib \drawText\)
  - This is visually clear but not a true edit
- **For v2, investigate true text stream editing:**
  - Requires parsing PDF content streams (Tj/TJ operators)
  - Requires matching font encoding (CMaps)
  - Consider using a different library or writing custom stream manipulation code
- **Set user expectations clearly** - document the overlay limitation in the UI

**Detection warning signs:**

- \drawText()\ draws new text but existing text is still visible underneath
- No pdf-lib API exists for \editText()\ or \eplaceText()\ - if you're looking for it, it doesn't exist
- Content stream manipulation requires low-level PDF knowledge beyond pdf-lib's API

**Phase to address:** Phase 4 (Text Editing) - this is the phase where the pitfall becomes critical

### Pitfall 6: Electron Main Process Freezes on Large PDF Operations

**What goes wrong:** pdf-lib operations (\load()\, \save()\, \copyPages()\) are synchronous CPU-bound operations in Node.js. When run in the Electron main process, they block the entire event loop, causing the UI to freeze completely. For a 100-page PDF, this can freeze the app for several seconds.

**Why it happens:** pdf-lib is pure JavaScript with no Web Worker support. All operations run on whatever thread calls them. In Electron's main process, this means blocking the event loop that handles UI updates, IPC messages, and user input.

**Consequences:**

- User clicks "Save" -> app appears frozen for 5+ seconds
- Windows shows "Not Responding" in the taskbar
- User thinks the app has crashed and force-quits
- All IPC messages are queued and processed after the operation completes

**Prevention:**

- **Run long pdf-lib operations in a Node.js worker thread** (not a Web Worker - pdf-lib doesn't support Web Workers):
  `javascript
  const { Worker } = require('worker_threads');
  // Offload PDF operations to a worker thread
  `
- **Show a progress indicator** during operations:
  - Use \ipcRenderer.send('operation-start')\ before the operation
  - Use \ipcRenderer.send('operation-progress', { progress })\ for long operations
  - Use \ipcRenderer.send('operation-complete')\ when done
- **Chunk large operations** using pdf-lib's \objectsPerTick\ option:
  `javascript
  await pdfDoc.save({ objectsPerTick: 50 }); // Async chunking
  `
- **Consider using \process.resourcesPath\** for efficient file I/O in Electron-packaged apps

**Detection warning signs:**

- UI freezes on save, merge, split operations
- Task Manager shows high CPU but no progress
- User reports "app froze" during PDF operations

**Phase to address:** Phase 2 (Page Manipulation) - merge, split, and reorder are the most expensive operations

### Pitfall 7: IPC Payload Size Limits for Large PDF Documents

**What goes wrong:** Electron IPC has practical limits on message payload sizes. Passing large PDF byte arrays (tens of MB) between renderer and main process via \ipcRenderer.invoke()\ can fail silently, corrupt data, or cause memory issues.

**Why it happens:** Electron IPC uses V8 message passing internally. Large ArrayBuffer transfers can exceed internal buffer limits or cause excessive memory usage in both processes.

**Consequences:**

- Large PDFs (>10MB) fail to transfer between processes
- App crashes with "Insufficient memory" errors
- PDF is partially transferred -> corrupted document

**Prevention:**

- **Keep PDF bytes in the main process** - the main process owns the \PDFDocument\ instance and file I/O. The renderer only requests operations and receives results.
- **Use file paths instead of byte arrays** for cross-process communication where possible:
  - Main process opens file -> stores bytes internally
  - Renderer requests operations -> main process operates on stored bytes
  - Renderer requests results -> main process writes to temp file and returns path
- **For rendering, use PDF.js in the renderer process** with the bytes passed once during document open, then cache in the renderer
- **Implement chunked operations** for very large documents

**Detection warning signs:**

- \ipcRenderer.invoke()\ returns \undefined\ for large documents
- Renderer shows errors about "message port closed"
- App memory usage spikes to gigabytes

**Phase to address:** Phase 1 (IPC Bridge + File I/O)

### Pitfall 8: XFA Forms Are Not Supported by pdf-lib

**What goes wrong:** Some PDF forms use XFA (XML Forms Architecture) instead of AcroForm. pdf-lib **cannot** read, fill, or flatten XFA forms. The form fields simply don't appear in \getForm()\.

**Why it happens:** XFA is a separate XML-based form format embedded in PDFs. Adobe created it as an alternative to AcroForm, but most PDF tools (including pdf-lib) only support AcroForm.

**Consequences:**

- User opens a tax form (IRS, government forms often use XFA) -> no form fields appear
- User tries to fill a form -> nothing happens, no error message
- User thinks the app is broken

**Prevention:**

- **Detect XFA forms on load** and show a warning: "This form uses XFA format and cannot be edited. Please use Adobe Acrobat."
- **List supported form types** in the UI: "Supports standard PDF forms (AcroForm). XFA forms are not supported."
- **Consider offering a conversion step** - some tools can flatten XFA to AcroForm, but this is complex

**Detection warning signs:**

- \getForm()\ returns empty fields for a PDF that clearly has form fields in a viewer
- PDF.js renders form fields but pdf-lib's \getForm()\ finds nothing
- PDF metadata contains \/XFA\ or \/XFDF\ references

**Phase to address:** Phase 2 (Form Filling)

### Pitfall 9: PDF.js Rendering Does Not Match pdf-lib Document Structure

**What goes wrong:** PDF.js and pdf-lib parse the PDF independently. They may disagree about:

- Page count (PDF.js may report more pages due to embedded thumbnails)
- Page order (some PDFs have non-sequential page numbers)
- Form field locations (PDF.js renders form fields as annotations; pdf-lib reads them from the form dictionary)

**Why it happens:** PDF.js is a rendering engine (what the user sees). pdf-lib is a document structure engine (how the PDF is built). They operate on different abstractions of the same document.

**Consequences:**

- User selects text on page 5 -> pdf-lib operates on the wrong page
- Form field values are applied to the wrong field
- Page thumbnails don't match the actual page content

**Prevention:**

- **Always use 0-indexed page numbers internally** and convert to/from 1-indexed for PDF.js API calls
- **Sync page state between PDF.js and pdf-lib** - maintain a single source of truth for current page index
- **Test with real-world PDFs** that have unusual structures (embedded thumbnails, non-sequential pages, named destinations)

**Detection warning signs:**

- Text selection highlights the wrong page
- Form values appear in unexpected fields
- Page thumbnails don't match the rendered page

**Phase to address:** Phase 1 (Document Manager)

### Pitfall 10: Digital Signature Workflow Is Fragile Across Libraries

**What goes wrong:** The digital signature feature requires three libraries working together: \pdf-lib\ (creates the signature widget), \
ode-forge\ (loads PFX certificate and performs RSA signing), and \signpdf\ (bridges them). Version mismatches between these libraries cause silent failures.

**Why it happens:** \signpdf\ is a thin adapter library with its own version compatibility matrix. \
ode-forge\ has undergone breaking changes. \pdf-lib\ changes its signature field API. There is no single authoritative source for which versions work together.

**Consequences:**

- Signature appears visually but is cryptographically invalid
- App crashes when loading a PFX certificate
- RSA signing produces incorrect signatures that fail validation

**Prevention:**

- **Pin exact versions** of signpdf, node-forge, and pdf-lib - do not use \^\ ranges for these
- **Test with a real PFX certificate** during development - self-signed certificates may have edge cases
- **Validate signatures after creation** - use a PDF validation tool or Acrobat to verify the signature is valid
- **Handle PFX password-protected certificates** - node-forge's \pki.pfxFromPkcs12()\ requires the password parameter

**Detection warning signs:**

- \signpdf\ throws "adapter not found" or "invalid signature" errors
- Acrobat shows "Signature is valid" for the visual signature but "Invalid" for the cryptographic signature
- PFX loading fails with "invalid PKCS12" errors

**Phase to address:** Phase 3 (Digital Signatures)

### Pitfall 11: Undo/Redo Memory Usage Grows with Each Operation

**What goes wrong:** The Command pattern requires storing snapshots of PDF bytes before and after each operation. For a 50MB PDF, each undo step doubles memory usage (before + after bytes). After 10 undo steps, that's 500MB+ of additional memory.

**Why it happens:** pdf-lib's \PDFDocument.save()\ returns a \Uint8Array\ of the entire document. Storing these snapshots for undo/redo is the only way to support true undo without re-computing operations.

**Consequences:**

- App memory usage grows unbounded as user performs operations
- Large PDFs (50MB+) cause memory exhaustion after moderate use
- Electron's V8 heap limit is reached -> app crashes

**Prevention:**

- **Limit the undo stack size** - cap at 20-50 operations (standard desktop app behavior)
- **Use WeakMaps or generation-based snapshots** - only store bytes for the current document generation
- **Clear undo stack on new document open** - don't carry undo history across documents
- **Consider compression** - store undo snapshots as compressed data (e.g., pako/zlib)
- **Monitor memory usage** and warn user if approaching limits

**Detection warning signs:**

- Task Manager shows memory usage growing with each operation
- App crashes with "JavaScript heap out of memory" after many operations
- Undo stack grows beyond reasonable limits

**Phase to address:** Phase 3 (Undo/Redo Command Pattern)

### Pitfall 12: PDF.js Text Layer Positioning Breaks on HiDPI Displays

**What goes wrong:** On Windows HiDPI displays (125%, 150%, 200% scaling), the PDF.js TextLayer (selectable text overlay) may be misaligned with the rendered page content. Text appears offset from where the user expects to click.

**Why it happens:** PDF.js uses device pixel ratio for rendering but the TextLayer positioning uses CSS pixels. If the transform between viewport space and CSS space is not correctly applied, the text overlay shifts.

**Consequences:**

- User tries to select text -> selection highlights the wrong area
- Text search results highlight incorrect positions
- User thinks the app is broken on high-DPI displays

**Prevention:**

- **Apply outputScale transform to TextLayer:**
  `javascript
  const outputScale = window.devicePixelRatio || 1;
  const transform = outputScale !== 1
    ? [outputScale, 0, 0, outputScale, 0, 0]
    : null;
  `
- **Test on multiple DPI settings** (100%, 125%, 150%, 200%)
- **Use PDF.js's built-in DisplayLayer** which handles scaling automatically

**Detection warning signs:**

- Text layer misalignment on Windows HiDPI displays
- Text selection highlights wrong characters
- Search results highlight incorrect positions

**Phase to address:** Phase 1 (PDF.js Rendering + Text Search)

## Minor Pitfalls

### Pitfall 13: Electron App Icon and File Association on Windows

**What goes wrong:** Electron apps on Windows can have issues with file associations (double-clicking a PDF opens the app but doesn't load the file) and app icons (missing or incorrect icons in Explorer and taskbar).

**Why it happens:** Electron Forge's Squirrel.Windows maker handles file associations, but configuration is non-trivial. App icons require multiple resolutions (.ico, .png) and correct manifest entries.

**Prevention:**

- **Configure file associations in Electron Forge config:**
  `javascript
  // electron-forge.config.js
  makers: [{
    name: '@electron-forge/maker-squirrel',
    config: {
      setupIcon: 'assets/icon.ico',
      // File association configuration
    }
  }]
  `
- **Test file association after building** - double-click a PDF and verify it opens in your app with the correct file loaded

---

### Pitfall 14: PDF.js Worker Loading in Electron Packaged App

**What goes wrong:** In development, PDF.js worker loads from \
ode_modules/pdfjs-dist\. After packaging with Electron Forge, the worker file may not be found because it's in a different relative path.

**Why it happens:** The packaged app has a different file structure than \
ode_modules\. The worker file path must be resolved relative to the packaged app's resource directory.

**Prevention:**

- **Resolve worker path using \process.resourcesPath\**
- **Copy worker files to the app's resources directory** during the build process

---

### Pitfall 15: pdf-lib \save()\ Without \updateMetadata: false\ Resets Document Metadata

**What goes wrong:** When loading an existing PDF and saving it, pdf-lib may reset or overwrite metadata fields (Title, Author, Creator, CreationDate) unless explicitly configured to preserve them.

**Why it happens:** pdf-lib's default behavior is to update metadata on save. If the original document had custom metadata set by the authoring tool, it may be overwritten.

**Prevention:**

- **Always pass \updateMetadata: false\ when loading existing PDFs:**
  `javascript
  const pdfDoc = await PDFDocument.load(bytes, { updateMetadata: false });
  `
- **Explicitly set metadata fields** you want to preserve or update
